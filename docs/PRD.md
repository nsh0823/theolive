# The O'live --- Product Requirements Document (PRD)

- **제품명:** 더올리브 (The O'live)
- **문서 버전:** 1.0
- **문서 상태:** MVP 기획안
- **작성 기준:** 단일 매장 운영을 위한 모바일 선주문 및 매장 주문 관리
  서비스

---

## 1. 제품 개요 (Overview)

### 1.1 제품 소개

The O'live는 단일 카페 브랜드인 더올리브의 고객용 모바일 주문 서비스와
매장 운영 서비스를 제공하는 앱이다.

고객은 모바일 앱에서 메뉴를 확인하고 옵션을 선택한 뒤, 매장 식사 또는
포장 여부를 지정하고 사전 결제할 수 있다. 매장 직원은 Store Web에서
실시간으로 주문을 확인하고 주문 상태를 관리한다. 점주 및 관리자는 Store
Admin에서 메뉴, 가격, 품절, 리워드, 매출 및 운영 정보를 관리한다.

### 1.2 해결하려는 문제

- 고객이 매장에 도착한 뒤 메뉴를 고르고 결제하면서 대기하는 시간을
  줄인다.
- 주문 옵션과 요청 사항을 표준화하여 주문 전달 오류를 줄인다.
- 매장 직원이 신규 주문과 제조 상태를 한 화면에서 빠르게 파악하도록
  한다.
- 스탬프와 쿠폰 포인트를 디지털화하여 고객 재방문을 유도한다.
- 소규모 단일 매장에 불필요한 다지점·본사 관리 기능 없이 필요한 운영
  기능을 제공한다.

### 1.3 제품 목표

1.  고객이 모바일에서 메뉴 탐색부터 결제까지 완료할 수 있다.
2.  결제 완료 주문이 매장 주문 화면에 안정적으로 전달된다.
3.  직원이 주문 접수부터 제조 완료까지 상태를 관리할 수 있다.
4.  점주가 메뉴와 품절 상태, 리워드 정책을 직접 관리할 수 있다.
5.  고객이 스탬프와 교회 발행 쿠폰 포인트를 확인하고 결제에 사용할 수
    있다.

### 1.4 제품 구성

---

제품 사용자 핵심 목적 주요 환경

---

Customer Mobile 고객 메뉴 탐색, 주문, iOS / Android
App 결제, 리워드

Store Web 매장 직원 및 실시간 주문 접수 태블릿 / 데스크톱
바리스타 및 제조 상태 관리

Store Admin 점주 및 관리자 메뉴, 리워드, 데스크톱
운영, 매출 관리
-----------------------------------------------------------------------

Store Web과 Store Admin은 기능과 화면 목적은 구분하되, MVP에서는 하나의
웹 프로젝트에서 경로와 권한으로 분리하여 구현한다.

- Store Web: `/orders`
- Store Admin: `/admin`

### 1.5 핵심 원칙

- **Single Store:** 매장은 하나이며 매장 선택이나 매장 변경 기능을
  제공하지 않는다.
- **Mobile First:** 고객 경험은 모바일 앱을 기준으로 설계한다.
- **Fast Ordering:** 메뉴 선택과 재주문 과정은 짧고 명확해야 한다.
- **Operational Clarity:** 매장 화면은 주문 상태와 처리해야 할 작업이
  즉시 보이도록 한다.
- **Minimal UI:** Toss와 같은 간결하고 직관적인 사용성을 지향하되 특정
  서비스의 UI를 그대로 복제하지 않는다.
- **Reliable Payment:** 결제 결과와 주문 생성은 서버에서 검증하고 중복
  처리에 안전해야 한다.
- **Separated Rewards:** 구매 스탬프와 별도 발행 포인트를 서로 다른
  자산으로 관리한다.

## 2. 사용자 및 권한 (Users & Roles)

### 2.1 고객 (Customer)

- 소셜 로그인을 통해 가입 및 로그인한다.
- 메뉴를 확인하고 장바구니에 담거나 바로 주문한다.
- 매장 식사 또는 포장을 선택하고 결제한다.
- 주문 내역과 알림을 확인한다.
- 스탬프, 교환 쿠폰, 쿠폰 포인트를 확인하고 사용한다.
- 계정 및 앱 보안 설정을 관리한다.

### 2.2 매장 직원 (Store Staff)

- Store Web에 직원 계정으로 로그인한다.
- 신규 주문을 확인하고 접수 또는 거절한다.
- 제조 상태를 변경한다.
- 주문 상세, 옵션, 수령 방식 및 요청 사항을 확인한다.
- 메뉴 품절 및 매장 운영 상태를 변경할 수 있다. (권한 설정에 따름)

### 2.3 점주 / 매장 관리자 (Store Admin)

- 매장 운영 현황과 매출 요약을 확인한다.
- 메뉴, 카테고리, 가격, 옵션 및 판매 상태를 관리한다.
- 스탬프 및 쿠폰 정책을 관리한다.
- 교회 발행 쿠폰 포인트를 등록·조회·조정한다.
- 공지사항, 영업 정보, 직원 계정을 관리한다.

### 2.4 권한 원칙

- 고객, 직원, 관리자 권한을 분리한다.
- 관리자 기능은 서버 권한 검증을 통과한 계정만 사용할 수 있다.
- 직원별로 주문 처리 권한과 운영 설정 권한을 구분할 수 있도록
  설계한다.
- 고객은 본인의 주문, 결제, 스탬프, 쿠폰 및 포인트 정보만 조회할 수
  있다.

- HOT / ICE 선택
- 장바구니

- 결제 및 결제 완료 화면
- 주문 내역
- 주문 관련 알림 및 공지
- 스탬프 조회 및 쿠폰 교환
- 쿠폰 포인트 등록 및 잔액 조회
- 쿠폰 포인트 결제 사용
- 더보기 및 계정 설정
- 앱 잠금 및 생체 인증 설정

#### Store Web

- 직원 로그인 및 권한 확인
- 실시간 신규 주문 표시

- 주문 접수 / 거절
- 제조 중 / 제조 완료 / 수령 완료 상태 변경
- 주문 상세 및 옵션 확인
- 매장 식사 / 포장 구분
- 품절 상태 빠른 변경
- 매장 영업 / 주문 가능 상태 변경

#### Store Admin

- 관리자 로그인
- 운영 대시보드 기본 지표
- 메뉴 카테고리 및 메뉴 CRUD
- 메뉴 가격 및 HOT / ICE 판매 설정
- 메뉴 품절 및 판매 상태 관리
- 주문 내역 조회 및 상세 확인
- 스탬프 적립 및 쿠폰 교환 정책 설정
- 쿠폰 포인트 코드 등록·조회·관리
- 기본 공지사항 관리
- 영업 정보 및 직원 계정 관리

### 3.2 MVP 제외 기능

- 다지점 매장 및 매장 선택
- 배달 주문
- 테이블 주문 및 QR 주문
- 고객 간 쿠폰·포인트 양도
- 기프트카드
- 멤버십 등급 및 등급별 혜택
- 복잡한 CRM 및 고객 세그먼트 분석
- 직원 근무표 및 급여 관리
- 본사 / 가맹점 통합 관리
- 외부 POS와의 양방향 연동 (별도 검토)
- 다국어 지원 (필요 시 후속 버전)

### 3.3 우선순위 정의

- **P0:** MVP 출시를 위해 반드시 필요한 기능
- **P1:** MVP 안정화 이후 추가할 기능
- **Out of Scope:** 초기 버전에서 구현하지 않는 기능

### 5.5 리워드 (Reward)

리워드는 **올리브 스탬프**와 **쿠폰 포인트**를 서로 다른 자산으로
관리한다.

#### A. 올리브 스탬프 및 교환 쿠폰

- 구매 실적에 따라 스탬프를 적립한다.
- 적립 기준은 관리자 설정값으로 관리한다.
- 스탬프를 정해진 수량만큼 모으면 쿠폰으로 교환할 수 있다.
- MVP 예시 정책:
  - 스탬프 10개: 아메리카노 또는 라떼 쿠폰
  - 스탬프 15개: 전체 음료 쿠폰
- 교환 쿠폰은 결제 시 현금성 할인처럼 사용하며 최종 결제 금액에서
  차감한다.
- 쿠폰별 사용 조건, 유효기간, 중복 사용 가능 여부는 정책으로 관리한다.

#### B. 교회 발행 쿠폰 포인트

- 관리자가 발급한 코드를 고객이 등록하여 포인트를 적립한다.
- 적립된 포인트는 결제 금액에서 직접 차감할 수 있다.
- 포인트는 스탬프와 별도로 잔액 및 사용 내역을 관리한다.
- 코드 중복 등록, 만료 코드, 잘못된 코드 등록을 방지한다.
- 포인트 발급·사용·취소 내역은 거래 원장(ledger)에 기록한다.

## 6. 핵심 사용자 흐름 (Core User Flows)

### 6.1 첫 로그인

```text
앱 실행
  → 소셜 로그인 제공자 선택
  → 외부 인증
  → 서버 인증 및 사용자 계정 확인
  → 최초 사용자 정보 설정 (필요한 경우)
  → 홈 화면
```

### 6.2 메뉴 주문 및 결제

```text
홈 또는 오더 탭
  → 카테고리 선택
  → 메뉴 선택
  → HOT / ICE 선택
  → 담기 또는 주문하기
  → 장바구니 확인 (담기 선택 시)
  → 매장 식사 / 포장 선택
  → 쿠폰 / 포인트 적용
  → 결제 수단 선택
  → PG 결제 진행
  → 서버 결제 검증
  → 주문 확정
  → Store Web 신규 주문 표시
  → 고객 주문 완료 화면
```

### 6.3 장바구니 담기

```text
메뉴 상세
  → 담기
  → 장바구니로 이동하기 / 계속 주문하기
      ├── 장바구니로 이동하기 → 장바구니
      └── 계속 주문하기 → 메뉴 목록
```

### 6.4 스탬프 쿠폰 교환

```text
리워드 탭
  → 스탬프 현황 확인
  → 교환 가능한 쿠폰 선택
  → 교환 확인
  → 서버에서 스탬프 잔액 및 조건 검증
  → 스탬프 차감
  → 쿠폰 발급
  → 보유 쿠폰 목록에 표시
```

### 6.5 쿠폰 포인트 등록

```text
리워드 탭
  → 포인트 코드 등록
  → 코드 입력
  → 서버에서 유효성 및 중복 등록 검증
  → 포인트 적립
  → 잔액 및 거래 내역 갱신
```

### 6.6 매장 주문 처리

```text
결제 검증 완료
  → Store Web 신규 주문 알림
  → 직원 주문 확인
  → 접수 또는 거절
  → 접수 시 제조 중
  → 제조 완료
  → 고객 수령
  → 수령 완료
```

## 7. 주문 및 결제 상태 정책

### 7.1 주문 상태

---

상태 설명 다음 가능한 상태

---

PENDING_PAYMENT 결제 대기 PAID, CANCELLED

PAID 결제 검증 완료, 매장 ACCEPTED, REJECTED,
접수 대기 CANCELLED

ACCEPTED 매장 주문 접수 PREPARING, CANCELLED

PREPARING 제조 중 READY

READY 제조 완료 / 수령 대기 COMPLETED

COMPLETED 고객 수령 완료 종료

REJECTED 매장 주문 거절 환불 처리 후 종료

CANCELLED 주문 취소 환불 상태는 결제와 별도
관리
-----------------------------------------------------------------------

실제 운영에서는 결제 성공 후 매장 거절이 발생할 수 있으므로, 거절 시
자동 또는 관리자 확인 기반 환불 흐름이 필요하다.

### 7.2 결제 상태

주문 상태와 결제 상태는 별도 필드로 관리한다.

- `READY`: 결제 준비
- `PAID`: 결제 완료
- `FAILED`: 결제 실패
- `CANCELLED`: 결제 취소
- `PARTIAL_REFUNDED`: 부분 환불
- `REFUNDED`: 전체 환불

### 7.3 예외 상황

- 결제 승인 후 앱이 종료된 경우: 서버의 결제 및 주문 상태를 조회하여
  복구한다.
- PG 결제는 성공했지만 주문 생성이 실패한 경우: 재처리 가능한 상태로
  기록하고 중복 주문을 방지한다.
- 매장 거절: 고객에게 알리고 결제 취소 또는 환불을 진행한다.
- 결제 후 메뉴가 품절된 경우: 매장 처리 정책에 따라 주문 거절 및
  환불한다.
- 실시간 연결 장애: Store Web은 재연결 후 미처리 주문을 다시
  동기화한다.
- 동일 요청 재전송: 결제, 주문, 포인트 차감, 스탬프 적립은 멱등성을
  보장한다.

- Store Admin은 데스크톱 사이드바와 테이블 중심으로 구성한다.
- 빈 상태, 로딩, 오류, 네트워크 끊김, 결제 진행 상태를 명시적으로
  디자인한다.

## 9. 데이터 모델 개요 (Core Data Model)

아래는 구현 전 검토를 위한 개념 모델이며, 실제 컬럼과 제약 조건은 ERD 및
마이그레이션 단계에서 확정한다.

Entity 주요 필드 / 책임

---

`users` 고객 계정, 소셜 provider 연결, 프로필
`staff_members` 직원 계정 및 역할
`store` 단일 매장 정보 및 영업 설정
`categories` 메뉴 카테고리
`products` 메뉴 기본 정보
`product_options` HOT / ICE 등 판매 옵션
`orders` 주문자, 주문 방식, 금액, 주문 상태
`order_items` 주문 당시 메뉴명·가격·수량 스냅샷
`order_item_options` 주문 당시 선택 옵션 스냅샷
`payments` PG 거래 ID, 결제 금액, 결제 상태
`refunds` 환불 금액, 사유, PG 환불 ID
`order_status_history` 주문 상태 변경 이력
`coupons` 쿠폰 정의 및 정책
`user_coupons` 고객별 발급 쿠폰 및 사용 상태
`stamp_transactions` 스탬프 적립·차감·복구 원장
`coupon_point_codes` 포인트 등록 코드 및 발급 정보
`coupon_point_transactions` 포인트 발급·사용·복구 원장
`notifications` 고객 알림
`announcements` 공지사항
`store_settings` 영업 시간, 주문 가능 여부 등 설정

### 9.1 데이터 설계 원칙

- 주문 항목에는 주문 당시 메뉴명, 가격, 옵션명, 옵션 가격을 스냅샷으로
  저장한다.
- 메뉴 가격이나 이름이 바뀌어도 과거 주문 내역은 바뀌지 않아야 한다.
- 스탬프와 포인트는 원장 기반으로 관리한다.
- 주문 상태 변경은 이력 테이블에 기록한다.
- 메뉴는 물리 삭제보다 비활성화 또는 판매 중지 처리를 우선한다.
- 모든 금액 계산은 서버에서 수행한다.
- 결제 및 리워드 거래에는 중복 처리를 방지할 참조 키를 둔다.

## 10. 비기능 요구사항 (Non-Functional Requirements)

### 10.1 보안 및 개인정보

- 고객은 본인 데이터만 접근할 수 있어야 한다.
- 직원과 관리자는 역할에 맞는 데이터와 기능만 접근할 수 있어야 한다.
- 데이터베이스 Row Level Security(RLS)를 적용한다.
- PG secret 및 서버 전용 키는 앱에 포함하지 않는다.
- 인증 토큰과 민감 정보는 안전한 저장소를 사용한다.
- 개인정보 처리방침, 이용약관, 회원 탈퇴 및 데이터 보존 정책을
  마련한다.
- 결제 및 포인트 관련 주요 작업은 감사 가능한 이력을 남긴다.

### 10.2 안정성

- 결제, 주문 생성, 포인트 사용, 스탬프 적립은 멱등성을 보장한다.
- 실시간 주문 수신이 끊겨도 재연결 후 서버 기준 상태로 복구한다.
- 주문 및 결제 상태는 서버를 단일 기준 데이터로 사용한다.
- 주요 실패 상황에 대한 로그와 모니터링을 제공한다.

### 10.3 성능 및 사용성

- 일반적인 메뉴 목록은 사용자가 기다림을 크게 느끼지 않도록 빠르게
  표시한다.
- 메뉴 이미지 크기와 포맷을 최적화한다.
- 주문 상태 변경은 매장 화면과 고객 화면에 신속히 반영한다.
- 매장 화면은 터치 조작이 쉽고 주문 처리 중 실수 가능성을 줄여야 한다.
- 네트워크 지연 및 오류 시 재시도 또는 현재 상태 확인 방법을 제공한다.

### 10.4 접근성

- 텍스트와 배경 간 충분한 명도 대비를 확보한다.
- 버튼은 터치하기 충분한 크기를 갖는다.
- 색상만으로 주문 상태를 구분하지 않는다.
- 스크린 리더를 위한 접근성 레이블을 제공한다.

## 15. 출시 전 확정이 필요한 정책 (Open Questions)

다음 항목은 개발 착수 전 또는 해당 기능 개발 전에 점주와 운영 담당자가
확정해야 한다.

1.  **스탬프 적립 기준:** 주문 금액 기준인지, 주문 1건당 적립인지, 특정
    메뉴 제외 여부.
2.  **스탬프 적립 시점:** 결제 완료, 매장 접수, 수령 완료 중 어느
    시점인지.
3.  **쿠폰 사용 정책:** 유효기간, 일부 메뉴 제한, 다른 할인과 중복 사용
    가능 여부.
4.  **쿠폰 가격 정책:** 아메리카노·라떼 쿠폰 및 전체 음료 쿠폰의 적용
    가격과 차액 결제 여부.
5.  **포인트 사용 정책:** 최소 사용 단위, 1회 최대 사용액, 유효기간,
    환불 시 복구 기준.
6.  **포인트 발행 정책:** 교회 발행 코드의 발급 주체, 일괄 발급 방식,
    만료 및 재발급 정책.
7.  **매장 식사 정책:** 좌석 번호 또는 테이블 번호가 필요한지 여부.
8.  **주문 거절 정책:** 재고 부족·영업 종료 등 거절 사유와 환불 처리
    방식.
9.  **주문 취소 정책:** 고객 취소 가능 시점 및 제조 시작 후 취소 가능
    여부.
10. **결제 PG:** 계약 PG, 지원 간편결제, 수수료, 취소·환불 API.
11. **알림 정책:** 주문 상태별 고객 푸시 발송 여부와 알림 채널.
12. **회원 탈퇴 및 보존 정책:** 결제·세무 관련 법정 보존 데이터와
    개인정보 삭제 범위.

## 16. 개발 시 유의사항

- 세 앱을 한 번에 완성하려 하지 않는다. 전체 구조와 데이터 계약을 먼저
  정한 뒤, 고객 주문 → 매장 처리 → 리워드/관리 기능 순으로 수직 단위
  개발을 진행한다.
- Store Web과 Store Admin은 별도 제품처럼 UX를 설계하되, MVP에서는
  하나의 웹 앱과 백엔드를 공유한다.
- 결제와 리워드는 금전적 가치가 있으므로 화면 구현보다 서버 검증 및
  예외 정책을 먼저 확정한다.
- PG 연동 전에는 테스트 결제 어댑터를 사용하되, 실제 PG 연동 경계가
  바뀌지 않도록 결제 인터페이스를 분리한다.
- MVP에서는 필요한 운영 기능만 구현하고, 다지점·CRM·복잡한 분석 기능은
  실제 운영 요구가 확인된 후 확장한다.
